## 1. Executive Summary

> **题库尚未按照「每一道独立试题」作为原子单位入库。更准确地说：`exam_questions` / `exam_papers`
> 为空，canonical question entity 从未被实例化；与此同时，上游语料本身也不具备可直接 ingest 的条件。**

The precise engineering verdict is **not** "atomicity schema failed". It is:

> **NOT ATOMIC / NOT INGESTED — atomicity cannot be established because the canonical question
> entity has zero persisted records, while the upstream corpus demonstrably violates
> one-question-one-record assumptions.**

```
Schema   : 🟢 supports atomic question (question_uid UNIQUE, paper FK, M:N KP)
   ↓
Source   : 🔴 not clean — two independently unhealthy branches
   ↓
Parser   : 🔴 produces duplication / merge / split / metadata corruption
   ↓
Ingest   : 🔴 never correctly executed against this DB (and is itself defective)
   ↓
DB       : 🔴 0 questions, 0 papers
```

### 1.1 The two upstream branches are independently unhealthy (P0-3)

This must not be collapsed into a single parser bug — they are **different defects in different
representations** and require **different fixes**:

```
database/parsed-examples/          (branch A — DB export, 45 JSON files)
    19,813 records
        ↓  dedup
    2,271 unique logical questions       → 88.6% source-level redundancy
    + 7 merged records, 80 split fragments,
      LaTeX stripped, mojibake, dead image refs

database/question-bank/            (branch B — per-question dir tree)
    1,239 question dirs (1,239 unique UIDs, 0 UID collisions)
        ↓
    881 stems are the literal string "undefined"   → 71.1% empty
    only 358 dirs carry real content
```

Branch A's disease is **duplication + structural corruption**.
Branch B's disease is **missing content**. Neither is a superset of the other.


> ✅ **The only unique constraints on `exam_questions` are `PRIMARY KEY (id)` and `UNIQUE (question_uid)`.**
> `(paper_id, question_number)` is a **plain btree index**. The database does **not** enforce
> "one canonical question per (paper, question_number)". → This is why **P0-QB-05 is required**.

### 2.3 `exam_papers`

PK `(id)`; **UNIQUE `(province_code, year, subject, exam_level)`**; `question_count` integer;
FK `province_code` → `provinces(code)`; `year`/`subject`/`exam_level` NOT NULL.

### 2.4 `question_knowledge_points` — cardinality

PK `(id)`; **UNIQUE `(question_id, knowledge_point_id)`**; FKs to both sides;
`relevance_score numeric(3,2) default 1.00`.
→ **Relationship is many-to-many (M:N).** Reported as observed; no architectural preference implied.

⚠️ Two competing representations coexist: the normalized M:N table **and** the denormalized
`exam_questions.knowledge_points` TEXT column. The ingest script writes **only** the denormalized one.

### 2.5 Orphan partition tables — latent split-brain

`exam_questions_y2019` … `y2026`, `exam_questions_ydefault` exist as tables, but:

```sql
SELECT ... FROM pg_inherits WHERE inhparent='exam_questions'::regclass;  → 0 rows
```

They are **not attached partitions** (they originate from `database/init/02-partitions.sql`, which
defines a *separate* `exam_questions_partitioned` schema). All 9 are empty.

### 2.6 What the system considers "one question"

**One row in `exam_questions`, identified by `question_uid` (UNIQUE), optionally linked to a paper
via `paper_id`, with options/answer/knowledge_points inline as JSON-encoded TEXT.**
The design is genuinely atomic-capable. It is simply unpopulated.

### 6.1 Duplicate — 🔴 SEVERE

Whole papers replicated verbatim with fresh surrogate IDs. `math_2021.json`: 651 records =
**31 contiguous ID blocks of exactly 21 questions**, only **4 distinct block signatures**.

| File | records | blocks | **unique blocks** |
|---|---:|---:|---:|
| `english_2021.json` | 2,712 | 31 | **6** |
| `math_2022 / 2023 / 2024.json` | 651 each | 31 each | **1 each** |
| `chinese_2025.json` | 835 | 31 | **2** |
| `politics_2025.json` | 504 | 24 | **4** |
| `biology_2024.json` | 252 | 12 | **2** |
| **TOTAL (45 files)** | **19,813** | **638** | **113** |

Blocks 0 and 1 of `english_2021.json` are byte-identical (same md5 over the whole block) — these are
the **same paper re-ingested**, not legitimate repeats across years/papers.

Corroborating tell: only the **first** copy of each question carries a populated `question_uid`;
replicas have `question_uid: ""` (`math_2021.json`: 21 populated out of 651).

### 6.2 Merge (multiple questions in one record) — 🔴 CONFIRMED, 7 cases

`math_2022.json` qn=3 — three independent questions concatenated into one `stem`, still labelled
`question_number = 3`:

```

A. 1 2   B. 1 2 -   C. 1   D. 1 -
4 己知函数 1 ( ) 1 2x f x = + ，则对任意实数 x，有（ ）
A. … B. … C. … D. …
5 已知函数 2 2 ( ) cos sin f x x x = - ，则（ ）
A. … B. … C. … D. …
```

Detected by ≥8 option markers in one stem: `english_2021` qn=21/24/28/31, `math_2022` qn=3,
`math_2023` qn=1, `physics_2022` qn=15.

### 6.3 Split (one question across multiple records) — 🔴 CONFIRMED, 80 cases

English cloze blanks stored as option-list-only records with **no stem**:

```
english_2021.json qn=105 → stem = "A. cleaner B. chemist C. nurse D. doctor"
english_2021.json qn=106 → stem = "A. grades B. meanings C. needs D. expectations"
english_2021.json qn=107 → stem = "A. brushed aside B. put to the test C. brought under discussion D. taken into account"
… 80 total
```

**Distinction respected:** compound Chinese 大题 with sub-parts `（1）（2）（3）` are **legitimately one
question** and were **not** counted as merges — e.g. `biology_2025.json` qn=21
(`学习以下材料，回答（1）~（4）题`) is correctly one atomic record.

### 6.4 `paper_id + question_number` uniqueness

Not evaluable in DB (0 rows). Structurally: ingest sets `paper_id = NULL` unconditionally, and the DB
has only a **non-unique** index on `(paper_id, question_number)` (§2.2). Therefore even after a
successful ingest, **`paper_id + question_number` would NOT uniquely locate a question** — every row
would collapse to `(NULL, n)`.

## 12. P0 / P1 / P2 Findings

### P0 — question entity wrong or unusable

1. **`exam_questions` = 0 and `exam_papers` = 0.** No question bank in the database.
2. **Consistent with never-ingested** — combined sequence + `pg_stat` + `stats_reset` evidence (§5.1);
   no evidence of prior insertion or deletion.
3. **Source corpus 88.6% redundant** — 19,813 → 113 unique papers / 2,271 unique questions.
   Ingesting as-is would create ~17,500 spurious "distinct" questions (each replica gets a different
   `question_uid` because `genUid` keys on the replica's unique `q.id`).
4. **`question-bank/` 71.1% empty** — 881/1,239 stems are the literal string `undefined`.
5. **Ingest hardcodes `paper_id = null`** — orphans 100% of questions from papers, destroying
   paper/province/year provenance and `paper_id + question_number` addressing.
6. **Math content destroyed** — LaTeX stripped → semantically empty stems and empty option labels.

### P1 — materially breaks personalization

7. **80 split records** (English cloze) — option-only fragments with no stem.
8. **7 merged records** — 2–3 independent questions in one `stem` under a single `question_number`.
9. **Province metadata contradictory** — file-level `paper_info.province_code` conflicts with
   per-question `question_uid` / `paper_file_path`; ingest reads a non-existent `q.province`
   → `province_code` NULL for ~88%.
10. **20.5% of unique questions have no answer** — auto-grading impossible for those.
11. **KP not normalized** — ingest never populates `question_knowledge_points`; source tags are
    chapter-level strings not matching `knowledge_points.id`, some plainly wrong.
12. **`(paper_id, question_number)` is not UNIQUE** — DB cannot prevent duplicate question numbers
    within a paper (§2.2).

### P2 — hygiene / format

13. **Mojibake** UTF-8→Latin-1 corruption in some 2021 records.
14. **Dead image references** — `[图片7_1]` placeholders, `question_images` = 0.
15. **98 stems <15 chars** (4.3%) — likely truncated.
16. **30.3% lack analysis/solution** — no tutoring explanation available.
17. **Orphan partition tables** — `exam_questions_y2019…y2026`/`ydefault` unattached
    (`pg_inherits` = 0 rows); split-brain risk.
18. **`rag_questions` holds only test rows** — RAG retrieval effectively unpopulated.

### 16.1 Note on P0-QB-05

Adding `UNIQUE (paper_id, question_number)` is correct **under the current one-question-one-record
model**, and the existing `idx_exam_questions_paper_number` does **not** express that business fact.

be **redefined** (e.g. `(paper_id, question_number, sub_index)`) rather than naively made UNIQUE.
This audit reports the fact; it does not implement the constraint.
