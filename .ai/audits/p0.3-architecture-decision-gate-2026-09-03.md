## 1. Constraint inventory (live SQL, information_schema + pg_indexes)

Enforced FKs (the ONLY ones in the whole decision space):

| FK | child col | parent |
|---|---|---|
| `practice_records_question_id_fkey` | practice_records.question_id (nullable) | exam_questions.id — ON DELETE SET NULL |
| `practice_records_session_id_fkey` | practice_records.session_id (nullable) | exam_sessions.id — ON DELETE SET NULL |
| `question_knowledge_points_question_id_fkey` | question_knowledge_points.question_id (NOT NULL) | exam_questions.id — ON DELETE CASCADE |
| `fk_qkp_kp_id` | question_knowledge_points.knowledge_point_id (NOT NULL) | knowledge_points.id |
| `exam_questions_paper_id_fkey` | exam_questions.paper_id | exam_papers.id |

PKs: exam_questions(id), exam_sessions(id varchar), knowledge_points(id varchar), practice_records(id), wrong_questions(id), rag_questions(id), question_knowledge_points(id).

UNIQUE:
- `exam_questions_question_uid_key` → **question_uid UNIQUE + NOT NULL, no default** (live).
- `rag_questions_content_hash_key` → content_hash UNIQUE (nullable col, unique index).
- `question_knowledge_points(question_id, knowledge_point_id)` unique.

NOT NULL facts relevant to decisions:
- `exam_questions.question_uid` is **NOT NULL with no default** in the live DB. Any writer that inserts into `exam_questions` without a `question_uid` fails (this is why the current API `createExamQuestion`/`batchCreateQuestions` in `api/handlers/exam-questions.js` — which do NOT supply `question_uid` — would fail today if the table were non-empty; the sole reason 0 rows exist is that no paper has ever been ingested in prod).
- `practice_records.question_id` / `session_id` are nullable → a practice fact can exist with NULL question link (FK is SET NULL semantics).
- `practice_records.knowledge_point_id` is a plain varchar, nullable, **NO FK** (db.js DDL also no FK).
- `wrong_questions.question_id`, `knowledge_point_id`, `session_id` all plain columns, nullable, **0 FK** (live constraint query returns nothing for wrong_questions).
- `rag_questions.knowledge_point_id` plain varchar, nullable, **0 FK**.

Indexes (practice_records): user, user+subject, kp, is_correct, created_at, subject — i.e. it is **already shaped as the analytics fact table** for user×kp aggregations. **No UNIQUE index beyond PK** on practice_records → the same (user, question, session) can be inserted twice (see D1 idempotency risk).

KP id format evidence (live):
- `knowledge_points.id` values look like `MATH-B1-314` (gaokao textbook), `MATH-Z0-001` (zhongkao), `BIO-G0-001`, … **0 rows match `kp_%`**.
- Vision prompts (`api/routes/vision-parse.js:48`) instruct the LLM to emit ids of the form **`kp_math_015`** — a format that **does not exist** in the seeded KP table. Exact-id validation therefore virtually never succeeds; only the name-ILIKE fallback (`findKnowledgePointByName`) can link, and that is coarse (chapter-level names like "第二章 基本初等函数(Ⅰ)" vs question-level inferred names like "二次函数的图像与性质").

**[CORRECTION-1]** The accepted audit said `wrong_questions` has a `knowledge_point_id` (vchar) matching `knowledge_points.id` type and that in exam-session the kp comes from `question_knowledge_points` (empty → null). Both remain true, but add the stronger fact: the KP *id vocabulary* the vision LLM is told to emit does not exist, so photo pipelines cannot resolve kp by the LLM's own id format.

## 3. The four decisions with evidence

### D1 — Canonical per-user answer fact: `practice_records` vs a new fact table vs status quo

Evidence:
- `practice_records` is the only fact table with **enforced FK to the canonical question identity** (`exam_questions.id`) and to a session (`exam_sessions.id`); it carries is_correct / user_answer / correct_answer / difficulty / time_spent / subject / exam_level; it is pre-indexed for user×kp aggregation; and it is the **only** table `/api/review/weak-points` reads.
- Its writer is single and transactional with `wrong_questions` (exam-session submit), preventing divergent writes.
- Weakness: no UNIQUE (user, question, session) → duplicate submission would double-count; current writer is only the exam-session submit endpoint, and today **no user UI drives that endpoint** (exam-mode.js legacy writes to `/api/questions` = wrong_questions only; dashboard photo writes nothing; F3 exam pages target `/api/exam/session/*` but the canonical photo dashboard does not).
- A "new fact table" would duplicate an existing, already-shaped, FK-anchored table and fork the weak-points consumer for no schema gain.

Options:
| D1 | choice | consequence |
|---|---|---|
| D1-A (recommended) | Canonical per-user answer fact = **practice_records** | No schema change. All Adapter work = write practice_records rows; weak-points works unchanged. Fix later: add a dedup guard (unique or check-then-insert) when session/question flows go live. |
| D1-B | New fact table (e.g. answer_facts) | New migration + new writer + re-point review/weak-points + duplicate the index set practice_records already has. No functional gain demonstrated. |
| D1-C | Status quo (three sinks, no canonical) | Photo learning loop stays broken (weak-points stays empty); keep as "documented tech debt". |

### D2 — Question identity: `exam_questions.id` vs `question_uid` vs other

Evidence:
- All **runtime** FK/aggregation links point to **`exam_questions.id`** (practice_records.question_id, question_knowledge_points.question_id, question_vectors.question_id unique). `question_uid` is UNIQUE+NOT NULL but is a **stable business key for the bank**, consumed by scripts, file paths (`saveQuestionFiles`), vectors metadata, and the uid backfill — not by the user-fact chain.
- `rag_questions.content_hash` identifies **shared RAG documents**, never a user's answer fact; no user column exists there.
- Photo-parse output has NO natural `exam_questions.id`: rag row is content_hash-identified; there is no content-hash → exam_questions.id mapping table today, and exam_questions is empty anyway.
- `question_uid` Rule A needs subject/year/province/questionNumber — a photographed standalone wrong question has no paper metadata, so uid generation for photo-derived questions would fall to a synthetic scheme (and uid is NOT NULL → every exam_questions insert requires one).

Options:
| D2 | choice | consequence |
|---|---|---|
| D2-A (recommended) | **exam_questions.id** stays the canonical Q identity for user facts; treat question_uid as the bank's stable dedup key (keep Rule A). | No FK change. Photo fact rows carry question_id = NULL (or matching bank id when a match is later found) — schema allows NULL. |
| D2-B | question_uid becomes the fact identity (replace question_id in practice_records FK) | Schema migration; practice_records currently FK to id (int) — changing to varchar uid breaks FK + all joins + vectors + question_knowledge_points (all keyed on id). High cost, no consumer benefit. |
| D2-C | rag_questions.content_hash becomes Q identity | Content table has no user/FK axis; weak-points joins on kp not content. Not viable as a user-fact identity. |

### D3 — Vision (photo) behavior: auto practice-record vs candidate (parse-only) vs user-confirm

Evidence:
- `POST /api/vision/parse` today returns parse + ingests to rag_questions only (auth user known server-side via `req.user`).
- A practice_records insert from a parse is schema-possible with question_id/session_id NULL and knowledge_point_id set from the (validated or fallback) kp.
- kp resolution today is unreliable end-to-end (prompted id format `kp_*` doesn't exist; name ILIKE is coarse) — see §1.
- Wrong-ness (is_correct=0) is **assumed** by the photo use-case ("user photographs a mistake"); parse itself never verifies the user answered wrong.

Options:
| D3 | choice | consequence |
|---|---|---|
| D3-A | **Auto**: parse → immediately write one practice_records row (is_correct=0, kp when resolvable) + keep rag ingest | One-shot UX (matches "拍照即入库" doc intent); risk: junk/noise rows when image is not actually a mistake; requires kp fallback to be honest (null ok). Weak-points lights up only for rows with kp_id non-null. |
| D3-B | **Candidate**: parse returns structured candidate; nothing persisted until a follow-up call | Zero data pollution; but dashboard photo today is /api/proxy (no persistence) — Adapter = new explicit confirm endpoint. Slower loop. |
| D3-C | **User-confirm**: UI shows parsed stem + inferred kp + answer, user taps "这道题我错了" → then write practice_records (+ wrong_questions) | Highest data quality; needs UI change on the photo modal (currently /api/proxy text-only). Best long-term; moderate effort. |

### D4 — wrong_questions role: projection vs independent collection vs eliminate

Evidence (CORRECTION-3): wrong_questions is live-read by dashboard counters, wrong-book list, knowledge-profile, learning-suggestions, gamification badges, class-analysis, legacy learning-path — but has **zero FKs**, its kp/question links are null in the only real row, and `/api/review/weak-points` deliberately ignores it.

Options:
| D4 | choice | consequence |
|---|---|---|
| D4-A (recommended) | **Independent curatorial collection** (the wrong-book), kept as the user-facing store; practice_records is the analytics fact; the two are written together in the exam-session transaction and (future) by the photo confirm flow | Clean separation: weak-points = practice_records; wrong-book = wrong_questions. Must keep dual-write transactional to avoid drift (already true in exam-session.js; replicate in new photo writer). |
| D4-B | wrong_questions becomes a **projection** (derived/read-only from practice_records) | Requires re-pointing 7+ live consumers or a sync job + FK discipline; wrong_questions schema (reviewed/mastered/error taxonomy) exceeds practice_records columns → projection would need extension. Heavier than D4-A. |
| D4-C | **Eliminate** wrong_questions; re-point everything to practice_records | Breaks wrong-book UX fields (reviewed/mastered/analysis_note/error_types/export), gamification count semantics, class-analysis teacher views — all depend on the collection. High blast radius for no decision-gate gain. |

## 4. Recommended coherent posture (decision combo) — ADVISORY

- D1-A + D2-A + D3-C (phased: D3-A acceptable as interim) + D4-A.

Read as one coherent target architecture:
> Canonical user answer fact = **practice_records** (FK to exam_questions.id; id stays canonical Q identity; question_uid stays the bank dedup key).
> Photo flow becomes: parse → **user-confirm** ("答错了 + 学科/知识点可改") → single writer writes practice_records AND wrong_questions in one transaction (mirroring exam-session.js:191+215), plus rag ingest for retrieval.
> weak-points consumer unchanged (practice_records). wrong_questions remains the user-facing wrong-book (no FK change).
> exam_questions population (0 rows) is a **separate upstream gate** — until the bank has rows, photo facts carry question_id=NULL and weak-points still work off kp.
